# Project Completion Status — Independent Audit

**Audit date:** 2026-10-22  
**Overall status:** **FAIL — prototype behavior is verified, but the application is not production-ready.**

This audit inspected the current source and exercised isolated Node.js and FastAPI instances. The prior completion report was not treated as evidence. Runtime API probes used disposable service processes on ports 3002 and 8001; the user's services on ports 3000 and 8000 were not used for state-changing probes.

**Gemini verification update (2026-10-22, supersedes the earlier no-key result below):** The key was in `.env.example`, which dotenv does not load; root `.env` was absent. The value was moved without display into the ignored root `.env`, and the example was scrubbed. Express also instantiated the Gemini module before its runtime dotenv call; a shared `server/loadEnv.ts` now loads root config before service initialization. The readiness diagnostic returned configured/providerEnabled true, with no key output. Actual generation using configured `gemini-2.5-flash` returned sanitized HTTP 404 (`GEMINI_MODEL_UNAVAILABLE`); the SDK model listing reported `generateContent`, but generation was not available for that configuration. A live request succeeded with `gemini-3.5-flash`, which is now the local setting and default. One separate structured request received HTTP 503; bounded retry for transient 5xx responses was added. The final required live test passed, and the real synthetic-PDF upload completed Gemini analysis through Express/FastAPI. The credential-like value had been present in a shared example: rotate it if it was a live key.

**Authentication/persistence remediation update (2026-10-22):** Express and FastAPI now validate OIDC JWTs using their respective JOSE libraries and map immutable subjects to server-configured identities/roles; token role claims and caller-controlled `x-user-id` headers are not trusted. Institution scoping and statutory approval/finding/admin permissions are enforced server-side. Demo switching now requires an explicit local-only opt-in and loopback access. Both services now use the same SQLite file by default (`data/aicte.sqlite`), with WAL transactions, a versioned schema-initialization record, indexed record projections, unique record/idempotency constraints, and application-version compare-and-swap. Express uploads persist their binary files under `data/documents`. New tests use locally generated OIDC signing keys and temporary databases; no real identity provider was configured or contacted. The React app can receive a short-lived token through its host integration, but this repository does not implement OIDC sign-in/callback or account provisioning. These changes improve the prototype but do not make it production-ready.

### Current authentication and persistence verification (2026-10-22)

- **OIDC authentication:** Python creates a local RSA-signed test token, verifies issuer/audience/expiry and uses a mocked asynchronous JWKS response. The mapped server role is institution-scoped even though the signed test token includes an `ADMIN` role claim. Express tests reject anonymous requests, forged role claims, missing mappings, and cross-institution access. No real OIDC issuer/JWKS service or production account map was configured.
- **Durable state:** Express tests persist an application plus document metadata, version, native evidence, Gemini analysis, finding, reviewer action, and audit event into a temporary SQLite database. They reopen it through a new `DatabaseStore` and a fresh Node process and assert those records survive. FastAPI tests reopen a temporary SQLite database through fresh store instances and a fresh Python process, then verify persisted state and stale-version rejection. These are database/process-reopen tests, not a full container deployment, backup/restore, or multi-host test.
- **Atomicity and concurrency:** Express rejects stale concurrent approval versions and a mocked durable-write failure returns `PERSISTENCE_FAILED` without retaining the attempted application. FastAPI tests reject stale compare-and-swap writes and roll back a failed document replacement. All database tests use temporary stores; they do not modify or reset the user's existing application database.
- **Current limitations:** both services share a SQLite file but own separate snapshots; Express is the application workflow source of truth and FastAPI serves extraction plus legacy endpoints. The frontend expects a trusted host to inject a short-lived bearer token; no provider-specific login/callback or account provisioning is included. At-rest encryption, production backups, failover, real OIDC provider operation, Playwright, and Docker image execution remain unverified. Production readiness therefore remains **FAIL**.

## Findings that block production use

1. **Trusted identity setup is incomplete for production.** API JWT verification and server-owned role mapping are implemented and tested with locally generated tokens, but no real issuer/JWKS or production subject-role map is configured. The React app relies on a trusted host to provide a short-lived access token; provider login/callback and account provisioning are not included.
2. **Durability is prototype-grade.** SQLite transactions, CAS, reload tests, and write-failure rollback are implemented, but there is no at-rest encryption, managed backup/restore, multi-host failover, or operational database monitoring. Express and FastAPI use separate service snapshots in the shared file rather than a unified relational domain model.
3. **OCR processing remains incomplete.** Native embedded PDF text and real Gemini analysis were verified end-to-end. Gemini sends at most 40,000 extracted characters; scanned documents require manual review because Tesseract is not installed.
4. **Limited document checks.** SHA-256 duplicates and selected date checks operate on existing or synthetic metadata. Cross-document reconciliation of institution names, certificate numbers, or dates is not implemented. Anomaly detection remains heuristic and separate from approval.
5. **Deployment/E2E gaps.** Playwright is absent, Docker is unavailable, and the Dockerfiles referenced by Compose are missing. Browser workflow and container deployment have not been verified.

## Demonstration steps (prototype only)

1. Install the existing Node and backend dependencies. Start FastAPI in one terminal: `backend\.venv\Scripts\python.exe -m uvicorn backend.main:app --host 127.0.0.1 --port 8000`.
2. Start Express in a second terminal from the repository root: `npm run dev`; open `http://localhost:3000`. Development role switching is a mock identity, not authentication.
3. Configure `GEMINI_API_KEY` only in the ignored root `.env` or Express process environment; optionally set `GEMINI_MODEL`. Start/restart Express and check `/ready` for booleans only. Open **Applications** and upload a valid digital-text PDF under 25 MiB. The UI shows native extraction, source evidence, and a separate Gemini status/result. Failed/pending analyses can be retried on the document card.
4. Run `backend\.venv\Scripts\python.exe -m pytest backend\tests -v`, `$env:AICTE_REQUIRE_GEMINI_INTEGRATION = "true"; npm run test:gemini`, `npm run lint`, and `npm run build`. The live test may incur provider charges and fails clearly if the key is unavailable.
5. Verification adapters are simulations and disclose that they are not official. Gemini output is non-authoritative. Scanned pages/images still require Tesseract; without it, they remain for manual review.
6. Exercise optimistic concurrency and rollback only with synthetic data. The rollback mode is a simulated failure branch; it is not a database transaction.
7. Do not use this prototype to issue real regulatory decisions, accept real evidence as verified, or store records expected to survive a restart.
